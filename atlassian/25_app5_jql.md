## 1. Продукт одной строкой

**JQL-функции, которых нет в Jira Cloud, — подзадачи, связи, эпики и дети по результату
другого запроса, история спринтов (добавлена/убрана из спринта, даты спринта), вложенные
функции — со свежестью результата в секунды, а не в десятки минут. Только Forge,
Runs on Atlassian.**

Рабочее название: **ArtUp Query** (ключ `com.artuplabs.query`, коммиты `JQL-<n>`).

## 5. Границы v1

1. Функции по запросу: `subtasksOf`, `parentsOf`, `linkedIssuesOf(query, linkType?)`,
   `epicChildrenOf` / `childrenOf`.

4. Страница приложения: справка по функциям, примеры, состояние обновления.
5. Лицензия ≤ 10 пользователей бесплатно; 26 языков; светлая/тёмная тема.

### Не входит в v1

- Поиск по тексту комментариев и вложений, математика по полям, сравнение полей — v1.1 по спросу.
- Jira Data Center.

## 6. Архитектура (гипотеза до J-G5)

- `jira:jqlFunction` с precomputation: функция получает аргументы и возвращает родной JQL
  (`key in (...)` / `id in (...)`); Jira хранит результат, приложение обновляет его через REST
  precomputation при событиях задач (триггеры `avi:jira:created|updated:issue`, `issuelink`).
- Чтение — `asApp` REST: `search/jql` + `bulkfetch`, порядок чтения из ArtUp Reports (id по 5 000,
  затем пачки по 100).
- Ядро — чистые функции без I/O: разбор аргументов, построение JQL, сопоставление событий
  с затронутыми precomputation.

### Что прототип выяснил для плана

1. **Результат > 1 000** — только деревом функций/условий (`parent in (…)`, вложенные страницы); плоские списки ключей > 1 000 Jira отвергает (400).
2. **Гонка обновлений** — запись «что изменилось» одной общей KVS-записью теряет события при параллельных триггерах; нужен журнал (ключ на событие). Первая задача плана — подтвердить 0 потерь на 150 изменениях; это критерий «полнота 100%» из §4.
3. **Массовые правки** — очередь событий Forge при досеве раздавала 45–97 событий/мин с задержкой до ~275 с. При bulk-изменениях клиента (импорт, массовое редактирование) свежесть в секундах не гарантирована: в листинге обещать «секунды для обычных правок», в приёмке — отдельный замер всплеска (инструментом с таймаутами и повтором сетевых ошибок).
4. **Холодный старт** на внутреннем запросе по 50 000 задач — 32–33 с (выше 25 с синхронного лимита функции) — вычисление уже идёт в асинхронной очереди; повторный поиск — секунды.
