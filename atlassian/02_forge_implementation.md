# Atlassian Forge: реализация и внедрение

Дата: 2026-09-15. Вход — вывод отчёта [01](../ideas/01_third_sphere_market_analysis.md):
третья сфера — приложения в B2B-маркетплейсах, заходим через Atlassian Forge.
Этот документ отвечает на три вопроса: **что надо**, **где релизим**, **как делаем** —
и сначала чинит то, что в 01 посчитано неверно.

## 0. Оценка отчёта 01

Проверял по документации Atlassian (первоисточник). Ниже — только то, что меняет решения.

### Подтвердилось

| Утверждение 01 | Статус |
|---|---|
| 100% выручки до $1 млн накопленным итогом с 01.01.2026 | ✅ подтверждено [П] |
| Условия 100%: нет модулей Connect, OAuth, Forge UI | ✅ подтверждено; Forge UI = UI Kit **или** Custom UI [П] |
| Дальше 84% (с 01.04.2026), 83% (с 01.10.2026) | ✅ подтверждено [П] |
| Порог выплаты $500, деньги в течение 30 дней после конца месяца накопления | ✅ подтверждено → кассовый разрыв 30–60 дней верен [П] |
| Годовая оплата ≈ 10 месячных, тарифы ступенями по числу пользователей | ✅ подтверждено [П] |

### Исправления

**1. Стоимость инфраструктуры посчитана не по той статье.** В 01 написано
«бесплатно 730 GB-часов в месяц на приложение, сверх — $0.00076850 за GB-час».
Это тариф **Forge SQL Data Storage**, а не вычислений. Реальная сетка биллинга
(действует с 01.01.2026), квоты **не пулятся** между приложениями и статьями:

| Статья | Бесплатно в месяц | Сверх |
|---|---|---|
| Forge Functions (вычисления) | 200 000 GB-секунд | $0.000025 / GB-сек |
| KVS чтения | 0.1 GB | $0.055 / GB |
| **KVS записи** | **0.1 GB** | **$1.090 / GB** |
| Forge SQL: вычисления | 1 час | $0.143 / час |
| Forge SQL: хранение | 730 GB-часов | $0.00076850 / GB-час |
| **Логи** | **1 GB** | **$1.005 / GB** |
| Object Store: запросы | 5 000 | $0.001353 / 1k |
| LLM | 0 кредитов | по модели |

Вывод «$0 хостинга» в целом уцелел, но не автоматически. Считаю по-честному:

- 200 000 GB-сек при 512 МБ памяти = **400 000 секунд функций/мес**. При 200 мс
  на вызов это ~2 млн вызовов. На 84 клиентах — с запасом.
- А вот **0.1 GB записей KVS — это ~100 000 записей по 1 КБ в месяц**, то есть
  **1 200 записей на клиента при 84 клиентах**. Приложение, которое синхронизирует
  что-то по расписанию или пишет состояние на каждое изменение задачи, пробивает
  этот потолок легко, и цена записи — $1.09/GB, самая дорогая строка в сетке.
- Логи: 1 GB ≈ 5 млн строк по 200 байт. Verbose-логирование в проде — вторая
  статья, где можно случайно заплатить.

**Следствие для архитектуры:** KVS — для состояния, а не для журнала. Всё, что
похоже на лог событий или историю, — в Forge SQL (хранение в 1400 раз дешевле записи
в KVS) или не хранить вовсе. Уровень логирования в production — warn, не debug.
Песочницы (до 5 на каждый прод-сайт) с 04.04.2026 не биллятся — бета-тестирование
бесплатно.

**2. Marketplace REST API оказался богаче, чем ожидалось.** Документация
объявляет v2 (`/rest/2`) deprecated с отключением в 410 Gone. Проверено
2026-09-15: **эндпоинт отвечает 200** и отдаёт без всякой авторизации установки
по каждому приложению, цены по всем ступеням, отзывы с текстом и датами и
признак Forge/Connect. Задача «недели 1–2» из плана 01 оказалась дешевле, чем
считали, и уже выполнена — см. [04](04_market_measurement.md). Когда v2 всё-таки
отключат, точка входа меняется в [tools/fetch_marketplace.py](tools/fetch_marketplace.py).

**3. Правило «приложения бесплатны до 10 пользователей» больше не действует.**
С декабря 2021 партнёр ставит на тир 1–10 любую цену, включая $0. Рыночная норма —
всё же $0 (land and expand), и я бы её держал: тир 1–10 как воронка, деньги с 11-го
пользователя. В модели 01 это ничего не ломает, но означает, что сегмент
«малые команды 10–50 мест» начинается не с нуля выручки.

### Чего в 01 нет, а решения зависят

**A. Воронки Atlassian не существует в документе.** Для Shopify посчитано всё:
визит → установка 3–8%, установка → оплата 8–18%, отток 5–12%, отсюда 4 800 визитов
листинга в месяц. Для Atlassian — только знаменатель: «33–84 клиента». Это цель без
пути. Пока нет модели «просмотры листинга → пробы (evaluations) → оплаты», нельзя
сказать, дешевле Atlassian или дороже.

Что известно: у партнёра в портале есть отчёт **Cloud conversions** —
(число evaluation-лицензий) / (число продаж) — и **бенчмарк по площадке** через
Marketplace REST API. То есть свою воронку мерить можно, но **только после листинга**.
До листинга меряется предложение (сколько приложений, какие цены, где старые
обновления), а не спрос. Отсюда порядок работ в §5.

Гипотеза, которую надо проверять первой: поиск внутри Atlassian Marketplace даёт
меньше органики, чем Shopify App Store, потому что покупателей на порядок меньше.
Значит трафик придётся делать **снаружи** — и здесь стыкуется вторая уже идущая
сфера (SEO-программирование), ровно как в 01 стыковалась с Shopify.

**B. Сроки допуска не замерены — а это 3–6 недель календаря.** В 01 честно
написано «проходимость Atlassian-ревью и сроки не замерены вовсе». Замерил:

| Шаг | Срок |
|---|---|
| Partner Verification (обязательна для всех, кто листится впервые после 02.06.2025) | до листинга, срок не публикуется |
| Начало ревью заявки | 5–10 рабочих дней |
| Аппрув | 10–15 рабочих дней (быстрее для Platinum/Gold/Silver — нас это не касается) |
| Security Self-Assessment | истекает через год, переподача обязательна |

Это добавляется **после** готового кода и **до** первой продажи. Плюс security-анкета
на каждую публикацию новой версии: fail-сигнал блокирует листинг.

**C. Ловушка мажорных версий.** Только изменение scopes/permissions делает версию
мажорной. Мажорная версия **не применяется автоматически** — нужен явный consent
админа, и bulk-апгрейд блокируется, если новые scopes повышают привилегии. Минорные
катятся сами на все сайты той же мажорной версии.

Практический вывод, который дешевле принять сейчас, чем через полгода:
**объявить в v1 максимально полный набор scopes**, который может понадобиться в
ближайший год. Добавленный позже scope = мажорная версия = половина клиентов
застряла на старой и не получает фиксов.

**D. Требование «без продаж и звонков» на Atlassian выполняется хуже, чем в 01.**
Покупатель — админ Jira в компании: цикл недели, часто внутренний security-review,
иногда счёт и PO. 01 это называет риском «медленный старт», но не говорит, чем
закрывается. Закрывается двумя механизмами платформы, и оба надо заложить
в архитектуру, а не надеяться:

- **Paid via Atlassian** — чекаут, счета, налоги и продления делает Atlassian.
  Переговоров о деньгах нет.
- **Runs on Atlassian** — бейдж на листинге, который снимает половину вопросов
  security-review. Выдаётся **автоматически** по манифесту, заявки не нужно.
  Условие: приложение использует только вычисления и хранилище Atlassian и **не
  делает egress**, кроме аналитики без пользовательских данных.

Условие RoA почти совпадает с условием 100% ревшары. **Одна архитектурная линия —
никакого своего бэкенда, никакого внешнего хранилища, никаких внешних LLM по
пользовательским данным — закрывает и деньги, и доверие, и отсутствие звонков.**
Это главный вывод проверки, и он должен стоять в 01 первой строкой, а не «5 700
приложений против 16 846».

**E. Сравнение плотности конкуренции некорректно.** 01 сопоставляет 5 700 приложений
Atlassian и 16 846 Shopify как меру тесноты. Но не нормирует на число покупателей:
магазинов Shopify — миллионы, инстансов Atlassian — сотни тысяч. Приложений на
покупателя может быть **не в пользу** Atlassian. Это надо померить в неделю 1–2,
а не принимать как аргумент.

## 1. Что надо

### 1.1 Жёсткие архитектурные требования

Не предпочтения — условия получения 100% выручки и бейджа RoA. Нарушение любого
ломает экономику из 01.

| Требование | Зачем | Как проверяется |
|---|---|---|
| Ноль модулей Connect в манифесте | 100% ревшары | ревью манифеста |
| Авторизация OAuth | 100% ревшары | манифест |
| Интерфейс на Forge UI (UI Kit или Custom UI) | 100% ревшары | манифест |
| Ноль egress с пользовательскими данными | Runs on Atlassian | `forge eligibility` |
| Хранилище только Atlassian (KVS / Custom Entity / Forge SQL) | Runs on Atlassian | манифест, код |
| Поддержка data residency хоста | Runs on Atlassian | наследуется, если нет egress |
| `licensing.enabled: true` + проверка лицензии в резолверах и фронте | платный листинг | ревью Atlassian |
| Полный набор scopes заявлен в v1 | не попасть в мажорную ловушку | ревью манифеста |

Аналитика допускается — но только без End-User Data. Практически: считать события
продукта (открыл экран, нажал кнопку), не содержимое задач и не имена.

### 1.2 Лимиты платформы, под которые проектируем

| Лимит | Значение | Что из этого следует |
|---|---|---|
| Таймаут обычной функции | 25 с | синхронный резолвер не тянет тяжёлую работу |
| Web trigger / action | 55 с | |
| Async events и scheduled triggers | до 900 с (по умолчанию 55 с) | **вся тяжёлая работа — сюда** |
| События из Forge Remote | 5 с | |
| Память на вызов | до 1 024 МБ (по умолчанию 512) | GB-секунды считаются от объявленной памяти |
| Payload вызова | 5 МБ | |
| Запрос с фронта / ответ на фронт | 500 КБ / 5 МБ | пагинация обязательна |
| Egress-запросов | ~100 на минуту рантайма | и их всё равно быть не должно |
| Строк лога | ~100 на минуту рантайма | |
| Вызовов на пользователя | 1 200 / мин | |
| Вызовов на инсталляцию | 7 000 / мин или 300 / сек | потолок для крупного клиента (200–1000 мест) |

Проектное правило: **синхронный резолвер только читает и отдаёт; всё, что дольше
секунды, уходит в async event**. Это же снимает риск по GB-секундам — считается
фактическое время, а не объявленный таймаут.

### 1.3 Состав приложения

```
forge-app/
  manifest.yml          # модули, scopes, licensing, permissions (egress — пусто)
  src/
    index.js            # точки входа: резолверы, триггеры
    domain/             # бизнес-логика чистыми функциями — сюда смотрят тесты
    storage/            # обёртки над KVS / Forge SQL, единственное место с I/O
    resolvers/          # тонкие: распарсил → вызвал domain → отдал
  static/               # Custom UI, если UI Kit не хватает
  __tests__/            # jest по domain/ и resolvers/
  .github/workflows/    # CI
```

Логика вынесена из хендлеров не из эстетики: резолверы Forge нельзя запустить
локально без туннеля, а чистые функции в `domain/` тестируются обычным jest за
секунды. Всё остальное — интеграционные проверки на dev-сайте.

### 1.4 Инструменты и аккаунты

| Что | Зачем | Когда нужно |
|---|---|---|
| Atlassian account + Developer Console | создать приложение | день 1 |
| `@forge/cli`, Node LTS | `forge create/deploy/install/tunnel/lint/logs/eligibility` | день 1 |
| Бесплатный dev-сайт Jira/Confluence | разработка и ручная проверка | день 1 |
| Marketplace Partner account | листинг | до подачи, ~месяц 2 |
| **Partner Verification** | без неё приложение не листится | **начинать заранее, срок непредсказуем** |
| API-токен Atlassian | CI и Marketplace REST v3 | неделя 1 |
| Домен + страница документации, privacy policy, канал поддержки | требования аппрува | до подачи |

## 2. Где релизим

Четыре канала, и они проходятся по порядку. Путаница между ними — главная причина,
по которой люди застревают перед первой продажей.

### 2.1 Среды Forge

`development` (по умолчанию) → `staging` → `production`. Развёртывание и установка:

```
forge deploy -e development     # forge tunnel работает только здесь
forge deploy -e staging
forge deploy -e production
forge install -e production --site <site> --product jira
```

Квоты и биллинг считаются по приложению, не по среде. Песочницы (до 5 на прод-сайт)
с 04.04.2026 из биллинга исключены.

### 2.2 Каналы раздачи по стадиям

| Стадия | Канал | Кто может установить | Ограничение |
|---|---|---|---|
| 1. Разработка | `forge install -e development` на свой dev-сайт | только контрибьюторы | — |
| 2. Бета у чужих | Sharing link из Developer Console (среда production) | любой админ по ссылке | **нельзя, если в манифесте уже есть `licensing` или приложение подано на листинг** |
| 3. Первые платящие / пилоты | Private (unlisted) listing | по прямой ссылке, платно | не виден в поиске |
| 4. Рост | Public listing | все | после Partner Verification + security workflow + аппрува |

**Ловушка на стадии 2, из-за которой план 01 может встать.** План говорит «первые 10
платящих клиентов». Но приложение с `licensing.enabled: true` нельзя раздать по
sharing-ссылке. Выбор один из двух:

- **Держать две сборки:** отдельный app id без лицензирования для беты, основной —
  для листинга. Бета даёт обратную связь, но не деньги.
- **Идти сразу в private listing** и получить платящих без публичного листинга.
  Медленнее на старте (нужна Partner Verification), но первые 10 клиентов —
  настоящие платящие, а не бета-тестеры.

**Берём второе.** Контрольная точка 90 дней в 01 требует *платящих*, а не
пользователей; бета-ветка даёт красивые цифры установок и ноль информации о том,
платят ли за это. Sharing-ссылку используем только как черновой прогон на 2–3
знакомых админах до подачи.

### 2.3 Версионирование

| Изменение | Версия | Что происходит с установленными |
|---|---|---|
| Код, UI, исправления, новые модули без новых scopes | minor | **катится автоматически** на все сайты той же major |
| Добавление / замена / удаление scope, изменение egress | **major** | не применяется; нужен явный consent админа; bulk-апгрейд блокируется при повышении привилегий |

Правило релиза: **мажорная версия — событие, которое планируется раз в год, а не
побочный эффект коммита.** Перед каждым релизом — diff манифеста; если изменились
`permissions`, релиз не едет, пока не решено, что это осознанный major.

## 3. Как делаем

### 3.1 Пайплайн разработки

```
ветка → jest (domain/) → forge lint → forge deploy -e staging → ручная проверка
      → forge deploy -e production → forge eligibility → релиз
```

- **Локально:** `forge tunnel` против dev-сайта. Работает только в среде development.
- **Юнит-тесты:** jest по `domain/`. Это 80% покрытия и единственное, что бежит
  за секунды.
- **Интеграционно:** установка на dev-сайт + ручной сценарий по чеклисту; при
  стабилизации — Playwright по dev-сайту.
- **`forge lint`** — обязателен до деплоя, ловит ошибки манифеста.
- **`forge eligibility`** — проверка права на Runs on Atlassian; в CI как гейт,
  потому что потеря бейджа = потеря аргумента, который заменяет звонки.

### 3.2 CI

GitHub Actions, секреты `FORGE_EMAIL` и `FORGE_API_TOKEN`, CLI в `--non-interactive`.

| Триггер | Шаги |
|---|---|
| PR | `npm ci` → `jest` → `forge lint` |
| merge в main | то же + `forge deploy -e staging` |
| тег `v*` | то же + `forge deploy -e production` + `forge eligibility` + diff манифеста на изменение permissions |

Гейт на permissions-diff в CI — тот же механизм, что «плохой замер закрывает нишу в
тот же день»: дешевле сломать сборку, чем разослать мажорную версию, которую никто
не подтвердит.

### 3.3 Наблюдение и стоимость

- `forge logs` — оперативно; уровень в production — warn (логи биллятся).
- Developer Console → **Usage and charges**: следить за KVS writes и логами, это
  две статьи, где перерасход вероятнее всего. Порог тревоги — 50% бесплатной квоты.
- Marketplace портал → **Cloud conversions**: evaluations → sales, своя воронка
  против бенчмарка площадки. Это единственный честный источник по воронке Atlassian;
  до первого листинга его не существует.

### 3.4 Чеклист допуска к листингу

Собирается параллельно коду, не после.

- [ ] Partner Verification пройдена (**начать в неделю 3, не позже**)
- [ ] Security-анкета заполнена, fail-сигналов нет
- [ ] Security Self-Assessment подан (напоминание о переподаче через год)
- [ ] Название без нарушения товарных знаков: «X for Jira», не «Jira X»
- [ ] Логотип, баннер, скриншоты
- [ ] Страница документации: установка и использование
- [ ] Privacy policy
- [ ] Канал и условия поддержки описаны в листинге
- [ ] Рабочий корпоративный email (требование для paid via Atlassian)
- [ ] Приложение не ломает и не тормозит UI хоста
- [ ] Приложение полезно без платных сторонних аккаунтов (или это явно раскрыто)
- [ ] Цены по ступеням выставлены; тир 1–10 = $0
- [ ] Marketplace Partner Agreement принят

## 4. План по неделям

Порядок 01 сохранён — сначала замер, потом код, — но с поправкой на сроки допуска:
**Partner Verification запускается параллельно разработке, иначе она становится
критическим путём.**

| Недели | Что | Гейт на выходе |
|---|---|---|
| 1–2 | Замер предложения: категории, число приложений, цены по ступеням, число и **дата** отзывов, дата последнего обновления. Marketplace REST **v3**; если публичного доступа нет — парсинг листингов. Нормировать плотность на число покупателей (см. §0E) | Список из 3 категорий, где отзывы у лидеров растут, а обновления старше года и оценка ниже 4.0 |
| 3 | Выбор ниши и **функции**, а не только категории: 10 отрицательных отзывов у лидеров = 10 гипотез о том, чего не хватает. Регистрация партнёра, **старт Partner Verification** | Одна функция, сформулированная как «делает X за Y кликов вместо Z» |
| 3–4 | Модель воронки по выбранной нише: цена, клиентов до $5 000, сколько проб это требует, сколько просмотров листинга. Если требуемый трафик выше того, что даёт вся категория — ниша отбрасывается | Ниша прошла или закрыта в тот же день |
| 5–9 | v1: манифест с полным набором scopes, domain-логика, UI Kit, лицензирование, тесты, CI. Черновой прогон по sharing-ссылке на 2–3 знакомых админах (сборка без licensing) | `forge eligibility` зелёный, `forge lint` чистый |
| 9–10 | Листинг: материалы, документация, privacy policy, security-анкета, подача | Заявка подана |
| 10–13 | Ревью Atlassian (5–10 дней до старта, 10–15 на аппрув). Параллельно — внешний трафик на листинг: то же, что делается в SEO-сфере | Private listing живой, первые платящие |

**Контрольная точка 90 дней (из 01, уточнённая).** Нет 10 платящих — смотрим,
на чём встали:

- встали на **допуске** (верификация, ревью) — это не отказ ниши, сдвигаем точку
  на срок блокировки и не меняем сферу;
- встали на **воронке** (просмотры листинга ниже модели вдвое) — сфера меняется
  на следующую из таблицы 01 без сожалений о вложенных часах.

Это единственная поправка к правилу 01, и она нужна потому, что 3–6 недель допуска
в исходной точке на 90 днях не учтены — по нему можно закрыть работающую нишу.

## 5. Экономика после проверки

Модель 01 остаётся в силе: выручка = чистый доход, пока не пройден $1 млн.

| Сегмент | Цена/мес | Клиентов для $5 000 |
|---|---|---|
| Малые (10–50 мест) | ~$30 | 167 |
| Средние (50–200 мест) | ~$60 | 84 |
| Крупные (200–1000 мест) | ~$150 | 33 |

Что добавилось:

- **Инфраструктура ≈ $0, но не безусловно.** Потолок — 0.1 GB записей KVS и 1 GB
  логов в месяц. При 84 клиентах это 1 200 записей на клиента; приложение с
  синхронизацией по расписанию туда упирается. Цена ошибки — $1.09/GB.
- **Годовая оплата ломает помесячную модель.** Год ≈ 10 месячных приходят разово.
  MRR как метрика перестаёт работать; считать ARR / 12.
- **Считать по 83%, не по 100%** — 01 уже это требует, и это правильно: 100%
  действует до $1 млн накопленным итогом и обусловлено архитектурой, которую можно
  случайно нарушить одним egress-вызовом.

## 6. Что по-прежнему не замерено

1. **Воронка Atlassian.** Нет публичных чисел «просмотры → пробы → оплаты». Свои
   появятся только после листинга, через отчёт Cloud conversions. До тех пор модель
   недели 3–4 строится на допущениях — и это самое слабое место всего плана.
2. **Цены по ступеням** взяты из логики тарифов, не из листингов. Первая задача §4.
3. **Срок Partner Verification** не публикуется. Поэтому она стартует в неделю 3.
4. **Плотность конкуренции на покупателя** не посчитана ни для одной площадки.
5. **Спрос на конкретную функцию** — по-прежнему не проверен. Гейт недели 3 —
   единственный механизм, который это закрывает, и он держится на чтении
   отрицательных отзывов, а не на замере.
