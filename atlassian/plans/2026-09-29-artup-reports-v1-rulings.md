# ArtUp Reports v1 — решения, принятые без владельца (rulings)

Формат: решение — почему — цена ошибки.

- Ruling R-X5: конкурентность загрузки вложений — параметр продукта (≥ 12), а не условие ворот X-G5; первая задача плана проверяет её через `requestJira` в браузере, запасной путь — `/attachment/thumbnail` — при 6 замер 140 с при пороге 120 с, при 12 — 67 с — cost if wrong: Word/PDF на 500 задач с картинками дольше 120 с.
- Ruling R1: предпросмотр на данных задач — только для Excel; для Word/PDF — скриншот шаблона — рендер 5 задач в .docx/PDF ради предпросмотра дорог и не лучше скриншота — cost if wrong: одна функция в v1.1.
- Ruling R2: `globalPage` содержит и мастер экспорта, и управление шаблонами двумя вкладками; отдельного модуля администрирования нет — меньше модулей манифеста и точек входа — cost if wrong: перенос вкладки.
- Ruling R3: свой .docx-шаблон на ядре docxtemplater (MIT) плюс свой код картинок и богатых полей, а не движок с нуля — ядро уже решает склейку разрезанных `w:r`, циклы и условия; лицензию проверить первой задачей — cost if wrong: свой движок той же схемы.
- Ruling R4: встроенных шаблонов 8 (бриф §4), а не 4 (бриф §5): 4 для Word/PDF + 4 набора колонок Excel — сходится с обоими разделами брифа — cost if wrong: четыре лишних набора колонок.
- Ruling R5: предел Word/PDF в v1 — 2 000 задач; Excel без предела — пик памяти 766 МБ уже на 500 задачах с картинками; вкладка браузера не должна падать — cost if wrong: пользователи с большими Word-отчётами делят выгрузку.
- Ruling R6: 50 000 задач в .xlsx проверяются на синтетике в ядре, без сети — засев 50 000 задач на dev ≈ 2,5 ч API-вызовов, сеть уже проверена на 10 000 — cost if wrong: скорость сети на 50 000 не замерена.
- Ruling R7: спецификация и rulings лежат в `atlassian/plans/` рядом с планом, как у Export, а не в `docs/superpowers/specs/` — бриф §9 — cost if wrong: перенос файла.
- Ruling R8: материалы фазы 0 и спецификация коммитятся в локальную ветку `reports-v1`, а не в `main` — правило «не сливать в main без владельца» — cost if wrong: none.
- Ruling R9: условие в .docx-шаблоне — `{{#поле}}…{{/поле}}`, а не `{{#if поле}}…{{/if}}` — docxtemplater требует, чтобы закрывающий тег совпадал с открывающим — cost if wrong: пользователи Mustache-синтаксиса привыкнут за минуту.
- Ruling R10: богатое поле внутри цикла — `{{@body}}` / `{{@comment}}`, тот же тег без `@` даёт простой текст; списки в своём шаблоне — абзацы с отступом и маркером, без `numbering.xml` — нумерация Word требует правки частей шаблона пользователя — cost if wrong: списки не «живые» в Word.
- Ruling R11: части шаблона — 150 КБ сырых байт (≈ 200 КБ base64), до 14 частей; ошибка синтаксиса показывается именем тега и пояснением docxtemplater, а не номером абзаца — лимит значения KVS 240 КБ; docxtemplater отдаёт смещение в тексте, а не абзац — cost if wrong: на 4 вызова больше при загрузке 2 МБ.
- Ruling R12: из внедрённого контракта правил действуют языконезависимые пункты (нет `//` в телах функций, короткий JSDoc, без ссылок на задачи/план в коде, формат коммитов, только локальная ветка); пункты про C#/xUnit/NSubstitute к JS-коду не применяются — тесты на vitest, как в Trace и Export — cost if wrong: none.
- Ruling R13: план и rulings — в `atlassian/plans/` (отслеживаемые), как у Trace и Export, хотя контракт по умолчанию кладёт планы в `temp/plans/` — бриф §9 прямо называет путь, прецедент двух приложений — cost if wrong: перенос файлов.
- Ruling R14: модель исполнителя — в заголовке каждой задачи: простые чистые модули, копирование паттернов, UI по готовому контракту, скриншоты и замеры — sonnet; ADF, рендеры Word/PDF, свой шаблон, конвейер, клиент Jira, права резолвера — opus; ревьюер — той же модели, что исполнитель — указание владельца 2026-09-29 — cost if wrong: лишний круг исправлений на sonnet-задаче.
- Ruling R15: `forge register` runs non-interactively with `-s 249db86b-0aa6-4b81-96ba-62341736ad15` (Developer Space ArtUp Labs, from `forge developer-spaces list`) — the space prompt cannot render without a TTY — cost if wrong: none (same space as Trace and Export).
- Ruling R16: `alt` of an ADF media node is never the file name (the attribute is absent), and `media.attrs.id` is a media-services UUID, not an attachment id; so the rendered HTML (`renderedFields.description`) becomes the primary strategy for mapping media nodes to attachments, in document order, and Task 6 swaps the order inside `createMediaResolver`; for the thumbnail form the HTML also carries `data-media-services-id` = the node's `id` next to the attachment id in `href`/`src` — measured on RPT-10001..10003, `apps/reports/docs/live-checks.md` — cost if wrong: images of issues with same-named attachments resolve to the first one.
- Ruling R17: manifest gets `read:board-scope.admin:jira-software` and `read:project:jira` in addition to the fixed list — `GET /rest/agile/1.0/board/{boardId}/configuration` lists exactly these two OAuth scopes in the Jira Software REST spec and `read:board-scope:jira-software` is not among them; both are read-only; the change forces a major-version redeploy (`forge lint` approval note) — cost if wrong: two extra read scopes shown in the install consent.
- Ruling R18: `createExportRun({ client })` also accepts a factory `({ onRetry }) => client`; the run passes its own `onRetry` and counts `stats.retries` from it — the Jira client takes `onRetry` only at construction, so a ready client gives the run no way to see its retries; a plain client object still works with `retries: 0` — cost if wrong: the run hook builds the client inside the factory instead of before the call.
- Ruling R19: the wizard finds a board's project for the template list by reading the board's first issue (board configuration → filter JQL → first id → bulkfetch `project`) only when the board entry carries no `projectKey`; a failed lookup lists templates without a project — the brief says "the board's project via the first read" and the board context usually has the project already — cost if wrong: three extra read requests when a board opens without a project, or project templates missing for such a board.
- Ruling R20: the Templates tab lists project templates and reads `getScopes` for every project of `GET /rest/api/3/project/search?action=edit` (read page by page, 50 per page), sending the keys to the resolvers in calls of at most 20 (`TEMPLATE_PROJECT_KEYS`, the resolvers' own cap); a failed project read leaves only personal and site templates — the brief names this request and the resolvers accept 20 keys, and a tab that manages templates only needs the projects the user administers — cost if wrong: a project the user can view but not administer shows no templates in the tab (the wizard still offers them); one extra request per 50 projects.
- Ruling R21: the author column shows the display name read once through `GET /rest/api/3/user/bulk` for the accounts of the listed templates (50 per call), and stays empty for an account Jira does not answer for — templates store only the account id and the brief asks for an author column — cost if wrong: an empty author cell for a deactivated user; covered by the existing `read:jira-user` scope.
- Ruling R22: the modal's "Open ArtUp Reports" navigates with `router.navigate('/jira/apps/<appId>/<envId>')`, both parts read from `context.localId` (`ari:cloud:ecosystem::extension/<appId>/<envId>/static/<moduleKey>`); when the id has another shape the button becomes "Close" — `docs/live-checks.md` §Contexts records no global-page route, so the documented Forge Jira global-page URL form is used and is unverified until checkpoint C1 — cost if wrong: the button lands on a Jira 404 and the route in `globalPagePath` needs one line changed.
- Ruling R23 (requires the owner's decision — see checklist item 9): the 2 000-issue Word/PDF limit stays in v1 for now, although the Node measurement of 2 000 issues with 2 003 byte-unique images (209 MB of image bytes) peaked at RSS 2 307 MB for Word (JS heap 2 116 MB, file 192 MB) and 2 163 MB for PDF (heap 787 MB, file 221 MB), both above the 1.5 GB alarm line — methodology: RPT has only 503 issues with images, so `acceptance.mjs --multiply 4 --limit 2000` serves each real issue four times under new issue and attachment ids with the real pixels, and every read gets its own PNG text chunk so the bytes are unique and neither the docx nor the PDF writer can de-duplicate them (a first run without unique bytes gave Word 1 557 MB with 257 media files for 2 006 drawings and understated it); Node RSS is only a proxy for a tab and includes the finished file, the seeded images average 104 KB and real screenshots (0.5-2 MB) would raise it — cost if wrong: a Chrome tab may run out of memory ("Aw, snap") on a Word or PDF export of about 2 000 issues with many images, and the user loses the run; follow-up if the owner's browser check fails: cap Word and PDF with images at about 1 000 issues, or switch to `/attachment/thumbnail` above 500 images, or build in parts.
- Ruling R24: Excel keeps the in-memory ExcelJS workbook in v1; no streaming writer — 50 000 synthetic issues (18 columns, description text in Latin, Cyrillic and CJK) finish in about 3.2 s with peak heap 1 397-1 399 MB (250 ms sampling plus a reading right after `renderXlsx`, two runs) (rows 112 MB, the rest is the workbook), under the 1.5 GB line but at 93% of it, and the real 10 003-issue file with the 15 default columns peaks at 151 MB heap — a streaming `WorkbookWriter` would flatten the curve but changes sheet assembly, summary sheet and grouping (all built after the last row), and the brief asks for a ruling only when the line is crossed — cost if wrong: 50 000 issues with more than about 20 columns or long text cells can cross 1.5 GB; follow-up: stream rows into `ExcelJS.stream.xlsx.WorkbookWriter` per sheet.
